# Releasing

A release is six native archives, one per target in [release.py](../scripts/release.py), plus `SHA256SUMS`, published as a GitHub release by [release.yml](../.github/workflows/release.yml) from `main`.

## Archive contents

Each archive holds one folder with four files: the executable, `README.txt` from [archive-readme.txt](../scripts/archive-readme.txt), `LICENSE` and `THIRD-PARTY-NOTICES.txt`. Windows and macOS archives are ZIPs; Linux archives are tar.gz. macOS executables are signed ad hoc, not with an Apple developer identity, and are not notarized. Windows executables use the bundled GNU LLVM runtime path described below.

`THIRD-PARTY-NOTICES.txt` is generated by [notices.py](../scripts/notices.py) and committed. It covers every crate compiled into the executable for any target, the Rust standard library and the linked MinGW and LLVM native runtime code, printing ordinary crate license texts once. It also bundles the pinned toolchain's complete official standard-library component notices, rendered as plain text without filtering or deduplication, with its MIT, Apache, BSD-2-Clause and Unicode license texts. Legal preformatted blocks retain their exact decoded text; nested file exceptions and source links retain their context. CI fails when it is out of date. Quality packages native host builds on macOS, Linux and both Windows architectures; its Linux job uses the same Ubuntu 22.04 baseline as releases.

## Windows build contract

Both Windows targets use native GNU LLVM Rust hosts, `x86_64-pc-windows-gnullvm` and `aarch64-pc-windows-gnullvm`. The archive platform names are `windows-x86_64` and `windows-aarch64`. The compiler version comes from [rust-toolchain.toml](../rust-toolchain.toml); `python scripts/release.py toolchain --target TARGET` prints the full Windows host toolchain identifier used by CI. The host includes the `rust-mingw` component and bundled `rust-lld` linker, so the application needs no Visual Studio or external C toolchain.

[.cargo/config.toml](../.cargo/config.toml) selects `ld.lld`, self-contained linking and `+crt-static` for these targets. This selects bundled open-source MinGW startup/support and static LLVM unwind code; the UCRT implementation remains an external Windows OS component. Release binaries need Windows 10 or later on x86_64, or Windows 11 on ARM64. The x86_64 target enables SSE3, CMPXCHG16B and LAHF/SAHF, as specified by the [pinned Rust target source](https://github.com/rust-lang/rust/blob/1.99.0/compiler/rustc_target/src/spec/targets/x86_64_pc_windows_gnullvm.rs). Do not remove those features or rebuild the standard library to claim an older CPU baseline.

Quality and release builds use an explicit native `--target` for compilation, tests and documentation. For the final executable, [windows_runtime.py](../scripts/windows_runtime.py) runs the link with a trace and map under `target/runtime-link/`, validates the selected startup and native runtime inputs against [windows-runtime.json](../scripts/licenses/windows-runtime.json), and writes a receipt bound to the executable's SHA-256. Packaging requires that receipt through `--link-trace`. Ordinary source installation uses Cargo directly; this wrapper establishes the package build boundary. Together, the runtime verifier and packager reject unreviewed or proprietary startup/runtime inputs, separate LLVM or Visual C++ runtime DLLs, delayed imports and unknown DLLs. The Windows system/UCRT import policy includes the API-set names used by the bundled runtime. DLL names alone cannot establish which static code was linked.

To build a Windows package candidate on its native host:

```text
python scripts/windows_runtime.py build --target x86_64-pc-windows-gnullvm --trace target/runtime-link/x86_64-pc-windows-gnullvm.json
```

Use the ARM64 target on an ARM64 host. Pass that receipt to `scripts/package.py --link-trace FILE` along with its target, version, repository, binary and output arguments. The workflows contain the complete packaging commands.

The consolidated notices retain the complete version-matched MinGW runtime notice bundle and applicable MinGW and LLVM grants, together with the complete Rust standard-library component notices. The reviewed build route ships no proprietary Microsoft CRT or startup implementation. Windows supplies its OS DLLs; no Windows DLL implementation is included in an archive. A toolchain or native dependency update requires renewed source/input and notice review, as well as native tests on both architectures.

## Prepare

Follow the [verification setup](verification.md#standard-checks) for local tools and temporary output. Use `python` in place of `python3` on Windows.

1. Set the workspace version in [Cargo.toml](../Cargo.toml), run `cargo update --workspace` to refresh workspace package entries in `Cargo.lock`, and review the lockfile changes.
2. Move the Unreleased entries of [CHANGELOG.md](../CHANGELOG.md) into a section headed `## [VERSION] - YYYY-MM-DD`. Its body becomes the release notes with surrounding blank lines removed; code indentation and Markdown hard-break spaces are preserved.
3. Run the [standard checks](verification.md#standard-checks) and `python3 scripts/release.py notes --version VERSION`.
4. Commit, push `main`, and dispatch the workflow from it:

```sh
gh workflow run release.yml --repo resoltico/AuditoryLab --ref main -f version=VERSION
```

## What the workflow does

`prepare` requires the dispatched commit to be `main`, clean, at the given version, with a dated changelog section. It refuses an already-existing remote release tag before starting the dependent jobs. The Quality workflow runs on the same commit. Each of the six `build` jobs runs on a native runner: it runs the tests in the release profile, builds the executable, and packages it with [package.py](../scripts/package.py), which checks the executable's CPU and file type, runtime libraries, Windows native link provenance and platform floor (including Linux GLIBC 2.35 or earlier and no RPATH/RUNPATH), reads the archive back, extracts it and runs the extracted executable. Each archive gets a build-provenance attestation.

`publish` runs only when everything else passed. It writes `SHA256SUMS`, refuses a version whose tag already exists, creates a draft release targeting the qualified commit, compares the uploaded assets' digests with the built files, and then publishes, which creates the tag. Enable immutable releases in the repository settings so published tags and assets cannot change.

## When publishing fails

Inspect the release state first: a command can fail after the server has published it. If it is published, verify its assets and provenance; never edit, retarget or replace it. Any correction needs a new version. If it is still a draft, delete only that draft and re-run the failed `publish` job using the qualified archives from the same workflow run. If any archive needs rebuilding, re-run the whole workflow so all six archives come from one run.

## Verify a release

Download every asset, check `sha256sum -c SHA256SUMS` (or `shasum -a 256 -c`), and verify an archive's provenance against the release commit. Replace `ARCHIVE` with its path and `COMMIT` with the full commit SHA at the selected release's tag:

```sh
gh attestation verify ARCHIVE --repo resoltico/AuditoryLab \
  --signer-workflow resoltico/AuditoryLab/.github/workflows/release.yml \
  --source-ref refs/heads/main --source-digest COMMIT
```

Checksums establish that the downloaded bytes match `SHA256SUMS`. The attestation check binds the archive to the specified source commit and workflow. Neither shows what was tested.

## Dependency updates

After changing dependencies, run `python3 scripts/notices.py` and review the diff of `THIRD-PARTY-NOTICES.txt` like code. A crate that publishes no license file needs an entry in [supplements.json](../scripts/licenses/supplements.json): its declared license and reviewed license files, copied from the crate's upstream repository at the published commit and pinned by SHA-256. Each supplement is bound to the published version, repository and VCS identity as well as its declared license and exact material bytes. Changes require a new source review; identity checks do not establish legal completeness. The linked libm source permission notices are retained in the consolidated file and checked against the reviewed source bytes.

The Rust standard-library block includes every component notice from the official pinned toolchain, plus a source-distribution link for provenance. Native MinGW and LLVM material is bound to the runtime sources used by that toolchain and checked against the final selected link inputs. A freshness or identity check establishes neither legal completeness nor native execution results; review the source grants and inspect the corresponding Quality and release jobs.
